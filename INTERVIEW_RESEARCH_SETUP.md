# Interview research setup and limitations

This is an integration in progress, not a validated production deployment. The checked-in Firestore rules cover the new collections only. **Do not deploy them as-is over an existing database**: Firestore rules are replaced in full, and these rules deny all legacy collections. Export and review the actual deployed rules, merge these rules with them, and audit the legacy paths for role and tenant isolation before deploying. The existing app previously accepted self-selected roles during registration, so neither its profile role nor institution is a trustworthy authorization source.

## Architecture

An administrator assigns Firebase Auth custom claims `collegeId` (stable, nonempty string) to each member and `role: "PLACEMENT_OFFICER"` to approved officers. A callable verifies claims and writes a company (deduplicated by normalized name and college), its roles, and a placement drive. The Android student screen listens to approved companies scoped by the college claim. A second callable verifies membership, role and company access, deduplicates requests transactionally, checks a seven-day cache and limits new requests. A Firestore creation trigger calls the Gemini API with Google Search grounding and stores a job status and separate question and experience documents. Generated practice is labeled. Source links are accepted from grounding metadata only, and unsupported lines are dropped. Status and subcollections are observed by the app. Progress belongs to the authenticated user.

The seven-day cache and model can be changed in `functions/index.js` (`GEMINI_MODEL` environment variable for the model). Keys never enter the Android app. Research is limited to five new jobs per user per hour, with one active job per company/role. An officer can request a refresh through the callable with `refresh: true`; the UI does not yet expose it. A failed or stale job can be requested again. A scheduled recovery function supersedes interrupted attempts after a 12-minute lease and retries failures with bounded backoff. This requires Cloud Scheduler configuration.

## Configuration

1. Install Firebase CLI and use Node 22. Enable Firebase Authentication, Firestore, Cloud Functions (Blaze plan), Eventarc, and the Gemini API / Google Search grounding for the selected project. Check provider terms and search grounding display requirements before production use.
2. Administer custom claims using the Firebase Admin SDK in a trusted environment, e.g. `getAuth().setCustomUserClaims(uid, {collegeId: 'your-stable-college-id', role: 'PLACEMENT_OFFICER'})`. Preserve any existing claims when updating. Assign students a `collegeId` and an appropriate student role. Force token refresh or reauthenticate after changes. Do not let clients assign claims.
3. In the project directory: `firebase login`, `firebase use placeverify-845fc`, `firebase functions:secrets:set GEMINI_API_KEY`, then enter the secret interactively. Enable billing and required APIs; configure service-account permissions as required by Firebase.
4. After merging and testing the deployed security policy: `firebase deploy --only firestore:rules,firestore:indexes,functions`. Deploying functions separately is `firebase deploy --only functions`. Do not commit the API key or local `.env` files.
5. Test with two colleges, authorized and unauthorized accounts and real public searches. Verify links and grounding behavior against actual provider responses and required Google Search attribution UI. No live end-to-end test has been performed.

## Important remaining work

- The initial source attribution algorithm requires Gemini grounding spans to cover each reported item; it does not independently verify that each sentence faithfully reflects the underlying page. Candidate summaries and questions need stronger provenance validation and source-specific extraction before production. Grounded sources may be unavailable, and a generated practice batch can be truncated or fail; fewer than 100 items is expected in those cases.
- Validate recovery, add monetary cost limits, stronger semantic deduplication, reliable role and round extraction, a roadmap and source frequency analysis, and an officer refresh control.
- Research output requires compliance review for search-grounding attribution, source terms, retention, and presentation. The code does not bypass paywalls or log in to sources.
- Existing user registration, legacy opportunities, applications, reports and deployed rules need a coordinated migration. The new company system does not migrate old drives automatically. This rules file intentionally refuses legacy access until it is merged with an audited policy.
- Add emulator security, authorization, cache/concurrency and Android UI tests, and validate with deployed Firebase and a real Gemini key before calling the feature complete. App Check must be registered and tested in the Firebase project before enforcement.

## Audit update (local work)

- Self-registration is limited in the Android client to `STUDENT`, and the app selects privileged navigation from Firebase ID-token custom claims rather than the writable user profile. This does **not** secure an existing installation by itself: legacy Firestore rules must prevent privilege-bearing writes and trusted servers must continue to verify claims. Existing account owners require administrator review; registration does not establish trusted college membership.
- Callable functions enforce App Check. Register the Android app and SHA-256 signing certificate in Firebase App Check, link Play Integrity, and validate Play Integrity availability for your distribution channel before enforcement. The app currently installs the Play Integrity provider for both debug and release builds. A debug build on an unregistered or unsupported device may be rejected; configure a debug provider in a debug-only source set and register its token if needed. Never use the debug provider in production. See https://firebase.google.com/docs/app-check/android/play-integrity-provider and https://firebase.google.com/docs/app-check/cloud-functions.
- Research uses three focused Google Search grounded requests and up to four practice-generation requests plus one optional enrichment request. Provider call and token counts are recorded per attempt. `MAX_RESEARCH_CALLS` sets a per-attempt request cap (default 10, maximum 12); this is not a monetary budget, global quota, or a protection against all billing overruns. Set project quotas and billing alerts independently. Up to three automatic retries are scheduled with increasing delays, each with a separate per-attempt budget; stale attempts are superseded after 12 minutes. Cloud Scheduler and its service account must be enabled and authorized. Rate limiting is per-user, not a global spending cap.
- Frequency is a count of distinct grounding link strings, not independently verified unique publications or company statistics. Grounding only associates provider-reported support spans with responses; it does not independently verify a page or establish that an experience is authentic. Search Grounding display/attribution and provider terms must be reviewed before use. Sources, experience details, round summaries, roadmap, deadline schedule and freshness are incomplete.
- Read-only migration inventory: with authorized application-default credentials for an explicitly selected development project, set `GOOGLE_CLOUD_PROJECT` to that project and run `node functions/migration-dry-run.cjs`. It counts existing documents and performs no writes. Review every proposed college membership and officer entitlement against an authoritative source; assign claims via Admin SDK only after review. Review announcements and obtain explicit officer approval before publishing into new collections. Existing `isVerified` is not proof. There is no automated apply migration.
- Local rules tests: from `functions`, with JDK 21+ selected, run `node node_modules/firebase-tools/lib/bin/firebase.js emulators:exec --only firestore --project demo-placeverify --config ../firebase.json "node --test tests/rules.cjs"`. Emulator JAR download requires access to Google Cloud Storage. These tests apply only to the proposed new rules; they cannot establish safety of the unknown deployed legacy rules.
- The checked-in rules remain an isolated proposal. Obtain deployed Firestore rules from Firebase Console > Firestore Database > Rules, save a copy outside version control if sensitive, review and merge them with the proposal, and run a complete legacy regression/security suite before any deployment. Do not run the deployment command above until the merge and explicit authorization are complete.


## Local Android emulator setup

`debug` builds use Auth `10.0.2.2:9099`, Firestore `10.0.2.2:8080`, and Functions `10.0.2.2:5001`; `release` builds use the normal Firebase configuration and Play Integrity. Ports are defined in `firebase.json`. These are local emulators, and this command does not deploy: `node functions/node_modules/firebase-tools/lib/bin/firebase.js emulators:start --only auth,firestore,functions --project placeverify-845fc --config firebase.json`. Run with JDK 21+.

In another PowerShell window, create the three local-only identities with `$env:FIREBASE_AUTH_EMULATOR_HOST='127.0.0.1:9099'; $env:FIRESTORE_EMULATOR_HOST='127.0.0.1:8080'; node functions/tests/seed-emulator.cjs`. Their email addresses are `student@placeverify.test`, `officer@placeverify.test` and `admin@placeverify.test`, with the emulator-only password `PlaceVerifyTest123!`; they all receive the local-college claim. The seed script refuses to run without both local emulator host settings.

The debug build uses Firebase's App Check debug provider. Even though the Functions emulator is local, its enforced callable still requires a valid App Check token. After launching the app, find the provider's `Enter this debug secret` line in Android Studio Logcat on your own machine and register that value in Firebase Console > App Check > Apps > Manage debug tokens for the Android app. Do not paste that debug token into chat or commit it. You need permission to manage App Check for the existing Firebase project. The release build never installs the debug provider. The Firestore emulator uses the checked-in proposed local rules only; no deployed rules are changed.

## Quota and cached results

A Gemini 429 is recorded as a shared provider cooldown. The app shows a friendly message and the provider's retry time when present; if no retry information is returned, a conservative one-hour cooldown is used. The scheduled recovery worker does not retry quota-exhausted jobs. A later manual request after the cooldown can create a new job. Existing completed or checkpointed results are kept under their original job ID and remain visible while a refresh runs or fails. Company and role selection opens an existing kit without first generating research. Stored result timestamps indicate when the displayed data was last collected.

Provider cooldowns and results are scoped to the current Firebase project; they do not replace provider-side quotas, billing alerts, or safeguards for other clients sharing the same API project. A provider can continue to reject requests after its stated retry time. The research worker stops generating practice batches once at least 100 distinct questions are available.
